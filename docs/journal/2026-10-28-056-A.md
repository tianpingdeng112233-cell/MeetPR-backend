## 实现

### 新负荷类型与兼容

- LOAD_MODES 加入 `free_weight` / `bodyweight`，DB 类型允许旧目标列为空；两种新模式存储时旧目标列为 null，强度以现有 target_rpe / rir_target / target_pct 列保存。
- 两模式可无强度，或仅带一个单值强度；值域/0.5 步进复用 034；拒绝具体重量、区间值、多个强度和非 pct 模式的 pct_anchor。PATCH 切换模式时清旧强度、重量、锚。
- `toPlanSet` 统一投影为 `rpe` / `10.00`，bodyweight 备注补自重标记；不把标记写回 DB。非新模式保留原响应，旧重量的 target_weight coalesce 不变。完整旧响应 inline snapshot 与新模式响应逐字段比较（唯一差异 load_mode）。
- **free_weight 的 rpe/10.00 是过渡占位，不是处方强度，也不添加误导的自重标签。** 前端本期仍门控；未来移除投影另卡。
- Create/PATCH/batch 共用 schema 归一：load_mode 空、rpe/10、备注匹配 `/自重|bodyweight/i` → bodyweight，去掉全部标记并 trim，纯标记置 null。PATCH 还在合并态归一，支持只补备注的旧写法。
- 旧客户端从 bodyweight 改回普通 weight/RPE：`legacyIntensityPatch` 清理新模式列并恢复旧形态；兼容 load_mode 省略/null。仅改次数/备注时保留处方。
- 为旧目标列 nullable 做必需的历史记录调用点适配：`createImportedHistory` 对无目标值的重量回落为 0，旧有数值行不变；这不是 052 plan-import 文件或规则修改。

## 2026-10-30 · D2 部署前旧端 load_mode 解码兼容返修

### Bug、根因与修正契约

Opus 在 PR #341 部署前发现：回填后的自重行通过 `toPlanSet` 直接返回 `load_mode: "bodyweight"`。已发布 iOS 1.0(27)/(28) 的 String enum 和 Android zod enum 均只接受原六种模式；未知值导致整份计划解码失败，影响学员与教练。若上线为 P0；本轮未合并、未部署。

根因是 CARD-A 第 3 项错误地要求「load_mode 字段如实给 bodyweight」，违背 SPEC §2 的「今天的形状」及 CLAUDE hard rule 8。先前快照测试也特意覆盖了 legacy fixture 的 load_mode，因而漏掉这处破坏。此次以 David 转交的 Opus 修正契约为准，不修改卡或 spec 正典。

- 所有组响应将 bodyweight 投影为 `load_mode: null`、`intensity_mode: 'rpe'`、`target_value: '10.00'`，复用 `bodyweightCoachNote` 添加自重标记，其余字段保持现有序列化结果。
- `free_weight` 仍明确返回 `free_weight`：最低版本提高前网页门控不允许创建，因此无需将其伪装成旧 enum。原有 rpe/10 过渡占位不变。共享投影旁已留一行注释解释两者区别。
- pending-revision 的任意嵌套 JSON 在读取时应用同一投影，兼容此前或此后存入的 bodyweight，包括内嵌 published snapshot；存储、版本、content_hash 保持不变。
- 写入未改：旧形状仍归一存储为 bodyweight；新形状仍存 bodyweight，库内不补投影标记。
