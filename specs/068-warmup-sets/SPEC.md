## 术语

**热身组（warm-up set）**：学员在某个计划动作的处方组之前自己加的组，用来热身。挂在那个计划动作上，只给学员自己看；不计入容量、e1RM、PR、当天进度，教练端任何地方都不出现。与「额外组」同属学员自加记录，但额外组会给教练看、会进统计。

## 已拍板（引用即约束）

1. 热身组只能由学员自己加，只能挂在教练排的计划动作上（自加动作、自己练的 adhoc 记录本期不支持）。每个计划动作最多 5 组热身组。
2. 不计容量、不参与 e1RM、不参与 PR 判定、不算当天进度，不进历史预填 / 重量建议的来源。
3. 教练端（App 与网页的所有教练读取路径，含总览、提醒、活动台账、聊天里引用的组）一律看不到热身组。
4. 热身组不能挂视频（上传接口对热身组拒绝）。
5. 教练在处方里写的 `plan_sets.set_type = 'warmup'` 本期不动，不与本标记合并（往后放的热身算法再定）。

## 数据模型

- `set_logs` 新增 `is_warmup BOOLEAN NOT NULL DEFAULT FALSE`。
- 热身组行的形态与额外组相同：`plan_exercise_id` 非空、`adhoc = false`、`set_index` ≥ 该计划动作的处方组数，另带 `is_warmup = true`。唯一约束沿用 `(student_id, plan_exercise_id, set_index)`，热身组与额外组共用处方之后的序号空间；先后顺序由客户端按 `is_warmup` 排（热身在前），后端不排。
- 约束：`CHECK (NOT is_warmup OR (plan_exercise_id IS NOT NULL AND NOT adhoc))`。
- **存量照护**：纯增量，存量行全部为 `false`，语义不变，不需回填。回滚段写在迁移尾注释（DROP 约束与列；回滚后热身组会变成普通额外组，进统计——仅 staging 演练）。

## 接口

- 学员记组接口（`sets-log`）请求体接受可选 `is_warmup`（缺省 `false`）。`is_warmup = true` 时：
  - `set_index` 必须 ≥ 处方组数，否则 422 `SET_WARMUP_INDEX`。
  - 同一计划动作已有 5 组热身组且本次是新行 → 422 `SET_WARMUP_LIMIT`。
  - 已存在的同键行 `is_warmup` 与请求不一致 → 409 `SET_WARMUP_CONFLICT`，不写入（不允许把额外组改成热身组或反之）。
  - 必须带 `plan_exercise_id`，不得是 adhoc，否则 422。
- 删除接口（`sets-delete`）：热身组按额外组的规则可删（`set_index` ≥ 处方组数本已满足）。
- 学员读取路径：响应体每行追加 `is_warmup: boolean`。
- 额外组上限「每动作 10 组」只数 `is_warmup = false` 的行；热身组上限单独 5 组。
- 视频上传 / 绑定到组：目标行 `is_warmup = true` → 409 `SET_WARMUP_NO_VIDEO`。

## 读取口径（逐个核对，结论写进 JOURNAL）

`src` 下读 `set_logs` 的 19 个文件全部过一遍，每个归入下面一类并在 JOURNAL 列表写明：

- **排除热身组**：e1RM（`domain/e1rm.ts` 及其调用方）、PR 判定、动作统计 / 容量、重量建议与预填来源、`sessionProgress` 与活动结算 / 活动台账、所有教练读取路径（含 `coach-rpe`、`coach-overview-alerts`、计划序列化的教练视图、聊天组引用、反馈读取）。
- **保留并透出 `is_warmup`**：学员本人的组读取、删除、计划交接（`plan-handoff`）里随动作搬运的记录。
- 任何不确定归属的读取方，默认排除热身组，并在 JOURNAL 标出待 Opus 复核。
